# «Авто» geneva: почему подборов идёт меньше выбранного

Записка на будущее: разобрано 2026-11-21 по живому роутеру (OpenWrt,
geneva_c 2.0.1, zapret-gui 0.26.03). Вопрос был «почему подбор виден
только у одного домена, хотя включено делить потоки на нескольких».

## Коротко

Одно подборное место на группу-очередь, а групп всего 8 — и они заняты
работающими стратегиями. Это не сбой: `_search_slots()` честно отдаёт
**минимум 1**, а свободных очередей нет.

```
слоты = max(1, min(workers, MAX_SEARCHES, max_groups − <живых рабочих стратегий>))
```

`GenevaAutoManager._search_slots()`, `core/geneva_auto_manager.py:1103`.

## Почему у группы ровно один подбор

`ga.plan_groups()` (`core/geneva_auto.py:1292`) отдаёт пару «адрес +
транспорт» **только первой** группе (`claimed`/`claimed_ports`): иначе
две пробные стратегии действовали бы на одни и те же пакеты, и подбор
мерил бы не свою стратегию. Поэтому каждая группа — это одна стратегия и
свой набор адресов, а «делить потоки» значит «взять ещё одну свободную
группу под пробную стратегию».

`assign_queues()` (`core/geneva_auto_apply.py:35`) раздаёт очереди:
стратегия с живым процессом остаётся на своей, новая берёт свободную из
`340..340+N−1`.

## Границы, которые нельзя двигать по отдельности

| Что | Значение | Где |
|---|---|---|
| `MAX_GROUPS` (по умолчанию) | 4 | `core/geneva_auto.py:120` |
| `MAX_GROUPS_LIMIT` | 64 | `core/geneva_auto.py:121` |
| `QUEUE_BASE` | 340 | `core/geneva_auto.py:122` |
| `ENGINE_WORKERS_MAX` (потоков профилей) | 64 | `core/geneva_auto.py` |
| `HOST_QUEUE` («по имени») | 404 | `core/geneva_auto.py` |
| `OBSERVE_QUEUE` (детектор) | 405 | `core/geneva_auto.py` |
| `MAX_SEARCHES` | 4 | `core/geneva_auto_manager.py:72` |
| `slot_workers()` | `max(1, min(2, workers // 4))` | `core/geneva_auto_manager.py:162` |

Очереди «по имени» и детектора стоят **сразу за** диапазоном профилей
(404 и 405), поэтому число потоков процесса профилей упирается только в
предел самого движка (`--ext-workers` 1–64), а не в наши константы.
Раньше они стояли на 348/349 внутри диапазона, и потоков было не больше
восьми — это ограничение снято.

Групповой путь (старые движки без `ext_profile`) занимает
`340..340+N−1`: `MAX_GROUPS_LIMIT = 64`, `geneva_auto_fw.QUEUES` =
`range(340, 404)` — весь диапазон до «по имени» и детектора. Потолок
подняли с рекомендованных 8 до полной ёмкости очередь-пространства
движка: валидатор больше не отказывает осознанному выбору.

Что нужно помнить при смене номеров очередей:

- подпись процесса «по имени» и детектора **не** содержит очередь, поэтому
  живой процесс пережил бы смену номера: перед «kept» проверяется
  фактическая `-q` в `/proc/<pid>/cmdline` (`_queue_matches`), при
  несовпадении процесс перезапускается;
- правила снимаются целиком (nft — `delete table`, iptables — цепочки
  `ZGGA_*` и ipset'ы с префиксом `geneva_auto_`), так что старые правила
  на прежних номерах уходят сами.

## Что видно на живом роутере

Снимок `/api/geneva/auto` (2026-11-21, 300 сервисов):

- `max_groups: 8`, групп запущено 8, у них **8 разных** рабочих стратегий;
- `search_slots: 1`, `search_slots_wanted: 4`, `counts.searching: 1`;
- 26 применённых сервисов укладываются в те же 8 стратегий;
- **один** сервис не попал ни в одну группу — `bt4gprx.com (QUIC)`,
  стратегия `[UDP:sport:*]-duplicate(tamper{UDP:load:corrupt}(duplicate,),)-| \/`:
  план урезан `max_groups` (проверка: `applied без группы по ключу: 1`).

## Как это выглядит в интерфейсе

Причина пишется под фазой карточки «Авто», а не в свёрнутом блоке
«Списки»: строка `geneva.auto.split_now` — «Сейчас подборов идёт {n} из
{m}: остальные группы заняты работающими стратегиями.»
(`web/js/pages/geneva.js`, `slotsLine`).

## Что изменилось: профили вместо групп (geneva_c 2.0 и новее)

Ограничение «8 стратегий» — следствие **нашей** схемы «одна стратегия —
один процесс», а движок умеет иначе. У geneva_c 2.0 есть профили
(`--ext-profile FILE`, фича `ext_profile`): один процесс с `--ext-workers
N` слушает очередь 340 и `N−1` соседних, а профиль сам отбирает пакеты
своим ipset-файлом и порт-фильтром. Предел — `XPROF_MAX 255`, а не восемь
очередей.

Так теперь работает «Авто» на подходящем движке
(`core/geneva_auto.plan_profiles`, `core/geneva_manager.auto_engine_apply`,
`Applier.apply_profiles`):

- профиль на стратегию, порядок файла — по важности сервисов; пробная
  стратегия — первая;
- очередь у всех профилей одна (`QUEUE_BASE`), правила различают их
  наборами адресов и порт-фильтрами, поэтому наборы теперь **свои у
  каждого профиля**, а не объединённые (иначе порты профилей не
  различить);
- диапазон очередей процесса `340..340+N−1`, где N — потоки
  (`--ext-workers`, 1–64): «потоков» столько же, сколько очередей;
  очередь «по имени» и детектор стоят за диапазоном (404/405), поэтому
  своего предела сверх движка нет;
- старые движки без `ext_profile` работают по-прежнему группами —
  `Applier` выбирает схему по `features(binary)`.

Цели по локальному порту (пиры, DHT) — отдельный профиль `…-peer-…`
**последним** и только «все порты сервера»: geneva сравнивает порт
сервера, а у пира в цели записан порт клиента (6881), и профиль с
адресами такой пакет не пропустил бы.

`_search_slots()` в режиме профилей групп больше не считает: у общего
процесса очередь одна (диапазон `340..340+N−1` на все профили), а пробная
стратегия — такой же профиль, как и рабочие, и первый подходящий профиль
забирает пакет. Поэтому предел подборов — слоты, а не занятые группы:
`min(workers, MAX_SEARCHES)`. Прежняя формула со свободными группами
осталась для движков без `ext_profile` (откат на группы).

Смена стратегии профиля на лету: у geneva_c с фичей `ext_profile_runtime`
(X6d) файлы переписываются и уходит `ctl reload` — процесс не
перезапускается, потоки не рвутся. Без этой фичи смена стратегии —
перезапуск процесса; смена порт-фильтра — всегда перезапуск, потому что
правила firewall стоят под старые порты.

## Если понадобится больше подборов

Варианты по возрастанию цены (ни один из них не понадобился: взяты
профили, см. выше):

1. **Освобождать группу на время подбора**: стратегию, которой меньше
   всего сервисов, снимать с группы и отдавать её пробной, потом
   возвращать. Требует, чтобы «Авто» умело ставить себя на паузу для
   одного сервиса без потери обхода на остальных.
2. **Вторая очередь на стратегию** (по две группы на стратегию, с
   разделением адресов) — дороже по правилам: наборов адресов станет
   вдвое больше.
3. **Сдвиг `HOST_QUEUE`/`OBSERVE_QUEUE`** дальше по номерам с расширением
   `MAX_GROUPS_LIMIT` — для группового пути. Для профилей такой сдвиг уже
   сделан: очереди «по имени» и детектора вынесены за предел потоков.

## Сколько «потоков» советовать

Кнопка «Авто» у поля «потоков движка» спрашивает
`GET /api/geneva/auto/workers-suggest` и заполняет поле советом —
сохранение остаётся за кнопкой «Сохранить», осознанно выставленное
число кнопка не затирает. Считает
чистая `suggest_workers(cpu, meminfo)` (`core/geneva_auto.py`):
`min(ядра, (MemAvailable − 24 МБ) / 4 МБ)`, не меньше 1 и не больше 8
(`WORKERS_SUGGEST_MAX`) — больше восьми домашнему роутеру не нужно, а
предел движка 64 остаётся для ручного выбора. Ядра старше 3.14 без
`MemAvailable` считаются по `MemFree` (осторожнее); нечитаемый
meminfo — 1 поток, как у `slots_for_memory` сканера. Фразу для тоста
собирает страница, сервер фраз не держит.

## Смежное: «Важно» — два разных механизма

Тот же разбор заодно: список `geneva.auto.lists.important` (маски, домены,
AS в настройках) и отметка «Важно» в меню «⋯» строки (`user_priority`
сервиса в книге, `state/geneva/auto.json`) — **разные вещи** с одинаковым
названием. Отметки отдаются полем `marked` в `/api/geneva/auto/lists`
(`GenevaAutoManager.lists_view()`, через `services_snapshot()`, чтобы
читались и при выключенном режиме).
